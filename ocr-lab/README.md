# 開発プレビュー用・レシートOCR検証画面

PaddleOCR v6 smallをiPhone Safariで試す独立画面。通常のくらしストックのOCRや登録画面は置き換えない。Macやアプリのインストールは不要。

公開先：開発プレビューの `ocr-lab/`。通常のPWA入口とは別URL。GitHub Pagesの既存配信を使用し、新しいサーバーを追加しない。mainや他ブランチには画面・モデルを追加しない。

## 利用手順

1. Safariで検証URLを開き、最初は同じR06写真を選ぶ。
2. 「拡大・グレー化」のまま「読み取りを試す」を押す。
3. 完了したら商品名・価格を原本と比較する。
4. 同じ写真で再度ボタンを押し、初回と2回目の所要時間を確認する。
5. 「検証サマリーをコピー（個人情報なし）」で、件数・一致判定・所要時間だけ共有できる。商品名や決済番号を含む全文コピーは原則避ける。自動送信はしない。
6. 同じ画面で別の写真を選択する場合はモデルを再利用できる。「写真と結果を破棄」はモデルも解放するため、次回は初回準備からやり直す。処理中の破棄は処理終了後に反映される。

写真・文字起こし・結果をlocalStorage、IndexedDB、Sheets、外部OCRサーバーに送信・保存する経路はない。公開モデル・実行ファイルは同じ配信元からGETする。モデルやコードの通常HTTPキャッシュと写真の保存は別である。既存PWAのService Workerがある場合は公開モデル・コードをキャッシュすることがあるが、写真はURLへ変換してHTTP配信しない。

## 測定上の注意

今回の画面は**選択写真全体**を処理する。PC測定は人が指定した部分領域であるため、PCの8.2%という数値をこの画面の精度と同一視しない。画像の拡大は最大2倍、描画用画像は最大360万画素・長辺2880pxに制限する。診断情報に実際の入力・処理サイズと倍率を残す。

初回はSDK約10.5MB、モデル約31.2MB、WASM約15MB等を取得する。初期化と読み取りを含む全体時間を表示し、SDK内部の推論時間は診断で区別する。`firstRun`を初回・再実行の識別に使う。画像のデコード時点のメモリや、Safariのピークメモリは取得できていない。12MBより大きい写真、開けない形式はエラーにする。

読み取りは商品・値引き・税の自動確定ではない。候補表示に既存の独立抽出処理を使うが、購入記録へ保存する操作は存在しない。誤字と個別明細の正確さは原本で確認する。

## ビルド・配信

- SDK 0.4.2、ONNX Runtime Web 1.31.1、Vite 6.4.1をlockfileで固定。
- JS実行はWASM、1スレッド。モデルは必要な操作後に初期化。
- OpenCV.jsの動的関数生成に必要な`unsafe-eval`を検証画面のCSPだけで許可する。接続先はselfのみ、フォーム送信・外部画像・外部スクリプトは許可しない。
- `npm ci --ignore-scripts && npm run build`で静的ファイルを生成。公開モデルを公式URLから取得し、ファイルサイズ・SHA256を確認して同じ配信元へ配置する。
- モデル・WASM・SDKの大きな生成物をGitに入れない。ライセンス本文と通知を配信物へ同梱する。
- `pages-previews.yml`は対象開発ブランチだけこのビルドを行う。mainのコピー処理やアプリのサービスワーカー、GAS・ログイン・Sheets設定は変更しない。

## 検査

ローカルではビルド・モデル整合性・UIのSDK遅延読み込み、同じエンジンの再利用、結果コピー、処理中破棄・古い結果の抑止、保存経路がないことを確認する（`tests/receipt-ocr-lab.mjs`）。Chromiumはこの作業環境では起動時SIGTRAPとなり、ブラウザ実行テストはGitHub Actionsの`OCR laboratory browser test`で実施する。

ブラウザ試験は公開レシートを含めず、ブラウザcanvasで生成したMILK/TOTALの画像を使用する。実WASM認識、初回・再実行、モバイル幅、クリップボード、破棄、同一配信元GETだけであることを検査する。iPhone Safariでの実写真・速度・メモリ不足の確認はユーザー実機で行う。

## 2026-10-31：実装7・登録商品に限定したOCRカタカナ表記ゆれ候補

- `receipt-product-matching.js` は、家庭内商品マスタ・店舗別別名の照合を先に行う。チェーンに紐付く完全一致SKUを候補の上位に表示し、商品名の完全一致が異なる商品を示す場合は競合として表示する。**候補の先頭でも未確定・ユーザー確認必須**。
- 完全一致しない長めのカタカナ／ひらがな商品名について、濁点・半濁点、小文字（ャ・ュ・ョ等）と中黒の有無を緩めた**弱い比較キー**で、**商品マスタに実在する名称だけ**を候補提示する。OCR原文・商品正式名を上書きしない。弱い一致は `name_suggestion` または複数候補の `ambiguous` とし、画面で根拠を明示する。小さな単語は弱い比較の対象外。
- OCR名とマスタ名の双方に容量などの数字がある場合、**数字の列が異なれば弱い比較や編集距離照合を禁止**。店舗固有SKUが他店舗でだけ登録されているとき、そのSKUの他店舗商品を曖昧な名前で自店舗一致と扱わない。
- 商品マスタに「豚こま切れ」、チェーン別名に「ブタコマギレ」が存在すれば、レシート名から正式名を提示できる。**任意のカタカナから正確な漢字を自動生成する機能ではない**。新しい別名を記憶させるには、将来の明示的なユーザー確認と既存GAS側の権限・書き込み安全確認が必要。
- `tests/receipt-product-matching.mjs` にリンドール型の合成的な誤読例、半角・小文字、容量不一致、濁点衝突、漢字正式名と登録別名の対応、SKUの競合時優先順位を追加。開発中のJS単体動作例は確認済み。**GitHub Actions全体テストおよび実機の精度向上は別途検証**。
