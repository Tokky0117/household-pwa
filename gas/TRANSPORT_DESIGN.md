# くらしストック：GAS通信仕様（開発・試験用）と設計履歴

更新：2026-10-28 ／ 対象ブランチ：`stage-a-ui-handoff-review`

> **現行仕様はこの冒頭を優先**。後半の「接続前設計」「v50〜v56」等は当時の検討履歴で、実際に接続成功した範囲・書き込み方式・未実装状況が現在とは異なる。実装は `gas/Code.gs`、`gas-api.js`、`live-operation-journal.js`、安全境界と測定結果は `TRANSPORT_DECISION.md` を確認する。

## 2026-10-28 時点の通信契約（現行）

### 採用構成と優先順位

- **構成を維持**：PWA（GitHub Pagesの既存画面）＋Google Apps Script（GAS）＋Google Sheets（12シート）。自宅サーバー／独自MCP／別の有料APIサーバー／別DBへの移行は行わない。優先順位は**追加費用なし、画面の即時反応、家庭データの安全性**。無料枠は無制限ではない。
- **現在実機で確認済み**：試験専用GASのHTML Service画面（`/exec?trial_read=1`）から `google.script.run` で試験Sheetsの読み取りと5シート計測が成功。以前、試験GASの隔離データへの在庫変更も別途成功。これらは **GASオリジンの試験UI** の結果。
- **別経路は未解決**：GitHub Pagesの通常PWA `fetch` → 試験GAS `/exec` は過去にCORS／ネットワーク制限エラーを観測。別のデプロイで読取成功した報告もあるが、同一設定・同一条件の恒常的な通信成功とは扱わない。**本番のGitHub Pages版PWAが常時安全にGASと同期できると主張しない**。試験用HTML ServiceをそのままPWA一般公開方式として採用したわけでもない。

### 通常PWA ↔ GAS のコード上のHTTP契約（本番接続未承認）

| 項目 | 現在のコード上の仕様 |
|---|---|
| リクエスト | HTTPS `POST /macros/s/{deploymentId}/exec`、本文はUTF-8 JSON文字列、Content-Type `text/plain;charset=utf-8` |
| リクエスト本文 | `{id_token, action, payload}`。日用品の書き込み時は `operation_id` を追加 |
| 認証・認可 | GASがGoogle ID tokenを検証し、`users.auth_subject` のGoogle `sub` と所属 `households` を照合。該当ユーザー・家庭が各1行でない場合は拒否。家庭を越えて返さない |
| 応答 | 成功 `{ok:true,data:{...}}` ／失敗 `{ok:false,error:{code,message}}`。HTTP 200でも `ok:false` をエラー扱い |
| `bootstrap` | `household_id`、`categories`、`item_groups`、`products`、`stores`、`sequence_no`。家庭で絞る |
| `sync` | `payload.after_sequence` を受け取り、`{sequence_no,changes:[...]}` を返す。対象家庭の変更のみ、番号順 |
| `item.create` / `item.update` | GASには復旧可能なジャーナル方式を実装済み。ただしクライアントの `LIVE_WRITE_ENABLED=false`、通常GASの `ENABLE_EXPERIMENTAL_WRITES` は未設定／falseを維持。**通常PWAからは送らない** |
| `product.create` / `product.update` / `product.move` | GASの入口に名前は残るが、実行経路は `WRITES_DISABLED` で拒否。通信・保存を完成扱いしない |
| 端末側の保護 | Google ID tokenはメモリ中のみ、URL・端末の未完了操作記録に含めない。15秒タイムアウト、1MiB相当の文字列長上限をアダプタに設定。`no-cors`、JSONP、トークン付きブラウザURLを採用しない |

`text/plain` はプリフライト回避の可能性があるだけで、CORS応答の読み取り保証ではない。クライアント実装は `mode:'cors'`、`credentials:'omit'`、リダイレクト追従。GAS ContentServiceはレスポンスを別URLへリダイレクトする場合がある。

### 認証セッション変更中の応答と画面データの扱い

- 通常PWAで `bootstrap` を送った後にGoogleログアウト／別アカウント切替／試作画面へ戻る操作があれば、**保留中の旧リクエスト結果を破棄**する。同じアカウントへいったん戻った場合も、再ログイン前のリクエストを復活させない。
- 読み取り通信中に別タブへ移動した場合は、**待機表示を即座に解除し、後着した応答を破棄**する。画面を移動した利用者を日用品タブへ戻さない。移動後に新たに読み取りを開始しても、古い応答で新しい家庭データ・表示を上書きしない。HTTPリクエスト自体を中断したと断定せず、通信結果のみ無効化する。
- 認証変更通知を受け取れなくても、画面再描画時に**取得中リクエストのGoogle `sub` も照合**して失効させる。結果受信時のGoogle認証・画面・セッション照合も維持する。
- PWAの `liveSnapshot` は**受信時のGoogle `sub` に紐づく一時メモリ**。Google Identityの `subscribe` 通知、再フォーカス、次の画面描画時に認証状態を照合し、ログアウト・期限切れ・アカウント変更があれば旧家庭データを消して端末内の試作表示へ戻る。これはデータ保存内容や既存の端末内試作データを変更しない。
- 保存の応答が遅れて届いた場合も、旧家庭の画面データは復元しない。**保存が確定した応答**の場合は該当する端末ジャーナルの操作IDだけを完了させ、結果不明のときはジャーナルを残して明示再送の原則を維持する。切替後に元アカウントへ戻って再送するには、先にその家庭の `bootstrap` を取り直す。
- 日用品一覧の表示では、リンク済み商品を表示ごとに商品全体から抽出する `O(日用品数×商品数)` 方式を、1回の対応付けを使う `O(日用品数＋商品数)` 方式へ変更。関連付けの行順・非表示商品除外・ローカル試作データ分離は維持。画面側の計算量改善であり、実Google Sheetsアクセス時間の短縮秒数ではない。
- オフライン `tests/live-view.mjs` で通信途中の退出／ログアウト／A→B→A／期限切れ／他家庭の再取得と、80日用品・400商品の関連付けを確認。`tests/live-operation-journal.mjs` で保存中ログアウト時の遅延受領・ジャーナル完了・旧家庭データの非再表示を確認。書き込みゲートは変更しない。

### 保存・失敗・同期の契約（コードと試験で確認する内容）

1. **先にUIを反映**し、非同期保存の結果が確定するまで「保存済み」とは表示しない。端末の通信異常・タイムアウトをもって未保存と断定しない。
2. 日用品の更新は**同じ `operation_id` と同じ `action/payload`** のみ再送可能。端末側の未完了操作はGoogle `sub` と家庭に紐づけたジャーナルに保持し、勝手に自動再送しない。異なる家庭・アカウント、記録破損、端末内保存不可なら拒否する。
3. GASのロック・`version` 競合検査・`processed_operations` の要求ハッシュで二重保存を防止する。`prepared` ジャーナルを**商品更新より先に保存**し、日用品→`change_log`→ジャーナル確定の順で処理。同じ家庭に未完了があれば別の操作を拒否し、元のIDで復旧する。
4. 日用品ID・操作IDの重複、変更途中の物理行移動、version・シーケンス番号不整合時は `RECOVERY_CONFLICT` 等で**安全停止**。勝手に別行を更新しない。
5. **認証付きの読み取り `bootstrap` / `sync` では、Googleトークン検証の後に`SpreadsheetApp.openById` を1回だけ実行**し、認証用 `users` / `households` と読み取りデータの各シートで参照を共有する。従来は `bootstrap` で計7回、`sync` で計3回（認証を含む）だったが、モックでは双方とも1回になった。1件ごとのセル取得回数は減らしておらず、シート内容は都度取得する。
6. **通常の在庫保存中に** `SpreadsheetApp.openById` はロック下で再度1回開き、その**同じSpreadsheetオブジェクト**を使う。認証時の参照はロック下で再利用しない。各安全確認の行・範囲は必要な時点で**再読み取り**し、リクエストをまたぐ恒久キャッシュは使わない。小規模シートは全列一括、大規模では必要行・列を優先し、断片化時は一括へ戻す。
6. 上記の保存方式・試験は主に**オフラインモック＋隔離試験**での確認。一般ユーザー向けの書き込み許可、端末間リアルタイム同期、レシート／値札保存、商品更新APIはまだ完成していない。

### PWAのオフライン起動とキャッシュ分離（2026-10-29）

- GitHub Pages版PWAは `?v=57` 付きでCSS・JSを読み込む。Service Workerは**実際に読み込むURLと一致する資産を事前保存**し、初回オンライン起動後のオフライン再起動を可能にする。これは試作データ表示用で、GASへのオフライン通信・同期が解決した意味ではない。
- `CacheStorage` は同じGitHub Pagesオリジンの本番と各プレビューで共有される。Service Workerの更新では**自分自身のキャッシュ世代だけを削除**し、`main` や他プレビューを消さない。プレビューのビルドは各ブランチのキャッシュバージョンを維持して専用名を付ける。
- オフライン時は正確に一致するバージョン付き資産のみを利用し、別の `?v=` の旧スクリプトを混在させない。アプリの入口以外のナビゲーションを別画面にすり替えない。失敗したHTTP応答をキャッシュに保存しない。iPhoneのホーム画面・圏外起動での実機挙動は未確認。

### レシート写真読み取りの独立試作（2026-10-29）

- iPhone実機で二度目の再試行後も「明細0件」が継続。行抽出だけでなくOCR入力画像の品質・レイアウト解釈を改善する必要あり。端末内で色付き背景の中央にある明るいレシートの横幅を推定・トリミングし、メモリ上のCanvasへ適度に拡大・グレースケール・コントラスト補正してOCR。環境非対応または失敗時は元写真へフォールバックする。Tesseractの改行モードと疎な文字列モードを条件付きで使い分ける。
- OCR抽出に失敗しても明細追加ボタンと元写真を維持。OCRが実際に認識した文字列の先頭最大4000文字を折りたたみ「診断用・未保存」で表示する（写真・全文・診断文字はサーバ・端末保存へ書き込まない）。会員番号などが混ざるため診断の共有時は個人情報に注意。Safariでの再実機成功はまだ未確認。



- 追加実機の一般スーパーのレシート（商品4点、値引き、外税8%、支払合計）で明細0件を確認。「品名 ¥298」や「A* 品名 ¥398」の日本語一般レシート行を抽出可能にし、合計額と値引きを商品として扱わない。品名と¥金額の改行分離も試験する。OCRエンジンそのものの認識精度は未検証。
- 明細0件でも写真確認画面で手入力追加を可能とし、支払合計がOCRで読み取れた場合は、明細候補合計との比較を表示。税込・税別・値引きの差異を確認する追加チェックを求める（明細の自動税込換算はしない）。
- **Googleログインの一時停止は開発プレビューのURLパス限定**：`/household-pwa/previews/stage-a-ui-handoff-review/` ではGIS外部スクリプトの読み込み、`KurashiAuth.configure`、`KurashiGasApi.configure` を行わない。本番mainは変更しない。設定画面は停止中を明示。既存のGASや認証機能のコード・設定は保持し、後で再開可能。


- iPhone実機のレシート読み取りでは、OCR結果に文字化け・極端に小さい誤価格・レシート総合計の明細誤抽出、店舗名の無根拠な推定があった。コストコの長尺レシートを含む複数段組明細を想定して、OCR候補抽出を慎重にする。商品行の前後関係・SKU/数量/単価/金額の一致を見て、クーポン行や合計行は商品候補へ含めない。実機精度の改善は今後の検証が必要。
- 店舗名は既知チェーン候補にのみ絞り、未知のOCR文字列を店舗名と表示しない。試作用チェーン候補にコストコを追加するが自動選択はしない。確定前の原本確認チェックを必須化。
- 端末内の試作保存がGoogle Sheetsへの保存ではないことを記録一覧・保存操作・完了通知で明示。誤って試作保存した1レシート単位の削除を確認ダイアログ付きで追加し、削除対象の明細のみを同時削除する。端末保存失敗時は記録を削除済み扱いにしない。

開発プレビューのPWA画面資産はv58へ更新し、OCRコードの追加に伴う古いキャッシュとの混在を防止。

- GitHub Pages開発プレビューのレシートタブに写真の撮影・選択を追加。無料のTesseract.js 7.0.0を**利用者が写真を選んだ時だけ**CDNから読み込み、日本語・英語モデルを用いてブラウザ内Web WorkerでOCRを行う。OCRエンジン・言語データの取得にはインターネットが必要。外部コードは実行されるが、写真をGoogle SheetsやOCRサーバーへアップロードする処理は追加しない。
- JPEG・PNG・WebPの12MB以下を対象とし、HEICなど未対応画像は明確に案内する。写真のObject URLや認識結果は**保存前のメモリのみ**に保持し、画面退出・破棄・リセット時に破棄。元画像およびOCR全文をlocalStorage、GAS、Sheetsに保存しない。
- OCRで推測した店舗名・日付・明細・価格は誤認識を前提として編集画面で必ず確認する。チェーンは自動確定しない。利用者が確定するまで記録へ保存せず、明示的な「試作保存」で既存の端末プレビューデータ `records` / `record_items` に1レシート・複数明細を原子的に記録する。登録済み商品に手動で紐づけた明細以外は価格比較へ反映しない。
- 1レシート複数明細の保存後は、端末内の記録一覧で明細件数・合計額を表示し、展開して各明細を確認可能。端末保存が失敗したらメモリ内データも更新せず、保存成功を偽装しない。従来の手入力レシート・値札の単一明細保存も同じ原子的な端末保存へ統一。
- 夫婦間同期・GASへのレシート保存・画像永続化・実レシートOCR精度は未確認。通常PWAのCORS問題や本番保存の有効化とは独立した試作で、既存の書き込み禁止を維持。

### PWA側の通信失敗・タイムアウトの扱い

- `gas-api.js` の読み取り通信は15秒のAbortControllerによるタイムアウトを維持。CORS／ネットワーク拒否、HTTP 503、JSONではないログインHTML、過大レスポンス、GASのエラー（例：`RECOVERY_REQUIRED`）、AbortSignalによる中断のすべてで、**アダプタが勝手にリトライしない**ことをオフライン試験で確認した。
- 通常PWAの `bootstrap` が初回失敗した場合は設定画面に留まり、読み取り再試行ボタンを表示する。既に成功した家庭データがある状態で再取得に失敗／再取得中／画面切替により中断した場合は、**最後に取得が確定した一覧を保持し「前回のデータ」と明示**する。失敗を「取得成功」と表示しない。再試行は利用者操作のみで、アダプタ・画面側とも自動再送しない。成功した再取得だけが一覧と取得成功表示を更新する。
- UIに出す読み取りエラーは固定の安全な説明に限定し、例外メッセージ全文、接続先URL、トークンを転記しない。ネットワーク・CORS・アクセス権限は原因未確定として案内する。これは通信障害の解決ではなく、利用者向けの状態表示と復旧導線である。
- ネットワーク遮断はCORSに限らず起こるため、エラー名だけで根本原因は確定できない。特に保存リクエストは失敗応答や通信切断が起きてもGAS側で確定済みの可能性がある。端末ジャーナルを維持し、ユーザーが同じ操作IDで明示的に結果確認・再送する方針を変えない。
- **変更は通信契約を維持した内部最適化と回帰試験の追加のみ**。リトライ機能や新しい中継サーバーは導入しない。HTTP送信自体のiPhone実機での恒常的な成功は別途確認する。

### GitHub Pages上の既存・試験用通信診断（ブラウザ読み取りのみ）

- プレビューの `gas-trial-connection.html` を使用する。新しいGAS/Sheets/中継サーバーを作らず、**既存の試験用 `/exec` URLを本人が画面に直接入力**する。URLはブラウザの保存領域、URLクエリ、ログに保持しない。家庭用GASの既知URLは拒否する。
- **GET診断**：`GET /exec`、`mode:'cors'`、`credentials:'omit'`、`cache:'no-store'`、10秒タイムアウト。IDトークン、家庭ID、操作IDを送らない。内容を画面へ転記せず、短い応答だけを形式判定する。`{"ok":false,"error":{"code":"POST_REQUIRED"}}` を受信した場合だけ、**GASのGET経路到達を確認**と表示する。
- GETでGoogleのログイン画面などのHTMLが返っても「GASが応答できた」とは扱わず、ネットワークエラーはCORS／権限／通信など原因未確定と表示する。GETの成功だけでは**認証付きPOSTや通常PWAの通信成功は証明できない**。
- **認証付きPOST診断**：既存 `gas-api.js` の `request('bootstrap')` のみ。カテゴリ5件と返却形状を検証し、日用品・商品・店舗の**件数のみ**を表示。書き込みアクション呼び出し禁止、トークンを端末保存・URLへ追加しない。検査結果に所要時間を表示するが、GAS内訳やRTTを正確に分離した数値ではない。
- URL変更／ログアウト中の非同期応答は、古い成功情報を現在のURL・認証状態の結果として表示しない。実ブラウザを模擬した `tests/gas-trial-connection-page.mjs` でGET成功・ログインHTML・ネットワーク失敗・URL変更競合・POST読取・書き込みゼロを検証。
- **安全境界**：この診断画面はGitHub Pagesからの通信だけを切り分ける。所有者限定GASの権限を公開へ変更したり、Google IDトークンをGET URLへ付けたり、試験保存フラグを有効化したりしない。実iPhoneでの検証は利用者が任意のタイミングで行うまで未確認。

## CORS障害を確認した時点の方針（2026-10-26）
- 試験用GASのWebアプリをGitHub Pages内の `gas-trial-connection.html` から `fetch(POST)` すると「通信エラー：CORSまたはネットワーク制限」となった。**個別の原因はブラウザネットワークログで未確定**だが、GAS ContentServiceのレスポンスはGoogle公式仕様により `script.googleusercontent.com` へリダイレクトされる。CORSヘッダーのないリダイレクト先を静的GitHub PagesのJSから読めない状況は構造的にあり得る。
- この問題をGoogle CloudのOAuthクライアント設定緩和、Webアプリの「全員」への公開拡大、JSONPでのトークン運搬、`mode:'no-cors'` による不透明レスポンス、ブラウザのCORS無効化では解決しない。
- 次の実装案を先に検証して選定する：**(A)** Apps Script HTML Serviceに試験UIを配置し `google.script.run` を使用（最初に試す。機能は試験専用・読み取りに限定）、**(B)** 信頼できる独立したHTTPSバックエンドを用意し同一オリジン／CORS／認証を適切に構成。通常PWAで実保存を有効にするには通信方式の再設計とセキュリティ評価が必須。
- 切り分け用に `testIsolatedTrialResultReadOnly()` を試験GAS用コードへ追加。エディタから実行すればGoogle Sheetsの試験後件数・在庫・履歴・受領記録を**読み取りのみ**で検証できる。期待ログ `ISOLATED_TRIAL_READ_ONLY_OK`。この関数はデプロイもGoogle IDトークンも不要、書込み設定も変更しない。
- 現行のGitHub Pagesの読み取り/保存アダプタは、試験GASとのブラウザ通信が通るまで実データ運用に使用しない。書込みゲート `LIVE_WRITE_ENABLED=false` を維持。稼働中の家庭用GAS・`main` は変更しない。
参考: https://developers.google.com/apps-script/guides/content （ContentService redirects） / https://developers.google.com/apps-script/guides/html/communication （HTMLService google.script.run）
