## 1. 保存要求を先に確定

- 利用者が原本を確認した1件のレシートを、親と最大30明細の `receipt-create-1` 要求として組み立てる。正本は既存の `records` と `record_items` の2シートを共用する。追加の保存用シートは作らない。

- `household_id`、親・子の永続ID、時刻、同期番号、保存済みフラグをユーザー入力・ChatGPT JSONから受け取らない。商品IDが確定していても最初の価格比較対象は `price_eligible=false` とし、価格集計への昇格を自動では行わない。
- 税別／税区分不明の明細額は原本を確認した税込値が得られるまで正式保存しない。合計があって不一致なら、個別値引きや税を推測して割り振らず保存を止める。

## 2. GAS一括書込の復旧手順（内部コード実装済み、公開入口は未許可）

1. クライアントは確認済み要求と操作IDを、Google subject・家庭IDに紐づく未完了操作ジャーナルへ**送信前に**耐久保存する。Web Locksで同ブラウザの重複クリック・複数タブ送信を防ぐ。結果不明の自動再送は禁止。
2. GASはユーザー認証と家庭検証を行い、LockService下で最新の家庭別マスタ・過去の `processed_operations` と要求ハッシュを検査。未完了の別操作がある場合は拒否。同じ操作IDで内容が違えば拒否。
3. サーバーが親ID・全子ID・変更通知ID・家庭別同期番号を決定し、まず `processed_operations` に完全な書込計画を `prepared` として保存。**この事前ジャーナルの永続化に失敗したら親子は一切書かない。**
4. 保存順は `records` の親1行 → `record_items` の子N行 → `change_log` 1件 → `processed_operations` の完了記録。同一IDの行があれば値を全列照合し、正しい既存行を二重追記しない。
5. タイムアウトや故障後は同じID／同じ要求だけで復旧。親しかないなら不足子を、子の一部まであれば残りだけを追加。既存行の家庭・価格・versionなどが違う、親がないのに子がある、変更通知があるのに親子が未完成、IDが重複する場合は復旧を停止。
6. 完了確認後、家庭別の記録を再取得して画面を更新する。別の操作IDで同じレシートを作り直さない。

`receipt-write-recovery-plan.js` は上の判定を**書込なしの純粋関数**にしたもの。GAS内部の `mutateReceiptSafely_` にも同等の親子書込・同一ID復旧処理を実装し、故障注入を含むモック試験を追加した。**実Sheetでの途中失敗からの復旧・時間制限・多端末同時使用は未証明**。
